# 의도적 결함 목록 (팀 전용)

문서 버전: v3.0 (2026-11-06)

> 시연 준비·개발·수정 커밋 작성용 정답표다. 메타포 플랫폼·엔진·AI 모델의 입력으로 넣지 않는다.
> 정상 기대 동작은 [기능 명세서](./FUNCTIONAL_SPEC.md), 행동·selector·실행 조건은 [Playwright 실행 계약](./PLAYWRIGHT_CONTRACT.md)을 사용한다.

v2 결함 6개를 제거하고 아래 결함으로 교체했다. production·dev에 같은 코드로 존재하며 기능 플래그로 끄지 않는다.
상품 한정 결함은 B03의 한정판 키보드 하나다. B04는 특정 상품이 아닌 공통 헤더 메뉴 결함이다.
나머지는 상품 종류와 진입 경로에 관계없이 발생한다. 로그인·실제 재고 제한·서버의 금액 계산·쿠폰 중복 검증·찜 API는 정상이다.

## 1. 현재 결함 6개

| ID | 위치·범위 | 필요한 행동 | 눈에 보이는 실제 결과 | 정상 기대·대조 |
|---|---|---|---|---|
| B01 | 장바구니 쿠폰, 모든 상품·혼합 장바구니 | 로그인 → 재고 있는 상품 담기 → 장바구니 → SAVE5000 입력 → 쿠폰 적용 | `쿠폰 확인 완료`는 나오지만 할인·적용 쿠폰·최종 금액은 그대로. 반복 클릭·칩 입력·Enter·새로고침 후 재시도도 동일 | 유효 쿠폰은 최초 1회 5,000원 할인. 서버 API의 최초 적용·중복 거부는 정상 |
| B02 | 장바구니 증가 버튼, 모든 재고 있는 상품 | 로그인 → 상품 담기 → 장바구니 → 해당 행의 `+` | `수량 확인 완료`는 나오지만 수량·행 금액·상품 합계·서버 상태는 그대로 | 상한 미만이면 수량이 1 증가해야 함. 상세에서 다시 담기는 정상. 2개 이상일 때 감소는 합계도 정상 갱신 |
| B03 | 한정판 키보드 상세 `/products/3` | `재입고 알림 받기` 클릭 | `재입고 알림 안내 확인 완료`는 나오지만 신청창이 열리지 않음 | 신청창 표시가 정상 기대. 직접 주소·새로고침·홈·검색·다른 어느 상품의 추천 링크로 진입해도 같은 결함. 품절 담기 버튼 비활성화는 정상 |
| B04 | 공통 헤더의 USB 허브 메뉴 | 상단 카테고리 또는 전체 카테고리 메뉴에서 `USB 허브` 클릭 | `카테고리 선택 확인 완료`는 나오지만 URL·현재 화면 그대로 | `/?q=허브`로 이동해야 함. 다른 카테고리·검색창의 허브 검색·직접 검색 URL은 정상 |
| B05 | 모든 상품 상세의 찜 버튼 | 로그인 → 상세의 `찜하기` 또는 `찜 해제` 클릭 | `찜 상태 확인 완료`는 나오지만 하트·버튼 문구·찜 개수·서버 상태 그대로 | 찜 상태를 반전해야 함. 처음 찜하지 않은 상태와 이미 찜한 상태 모두 발생. 찜 목록의 해제와 서버 API는 정상 |
| B06 | 모든 상품의 배송 안내 팝업 | 상세 → 배송 안내 → `X` 또는 `확인` | `닫기 요청 확인 완료`는 나오지만 팝업·배경 잠금 그대로 | 팝업을 닫아야 함. Escape·배경 클릭·실제 뒤로 가기/라우트 이탈은 정상적으로 닫고 잠금 해제 |

B01/B02/B05에는 로그인이 필요하다. B01/B02는 장바구니에 실제 상품이 있어야 한다.
엔진 계정의 장바구니가 채워져 있다고 가정하지 않는다. 재현 단계에 상품 담기·장바구니 이동을 포함한다.
B02는 현재 수량이 `maxQuantity` 미만일 때 검사한다. 상한에서 `+`가 비활성화되는 것은 정상이다.
B04는 이미 허브 검색 결과에 있는 경우 이동 전후 차이를 구분할 수 없으므로 홈이나 다른 검색·상세에서 검사한다.

## 2. 처리 완료와 결함 결과 구분

클릭의 무접수와 처리 지연을 혼동하지 않도록 실제 기능 결과와 독립된 중립적인 확인 문구를 둔다.
확인 문구는 할인·찜·닫기 성공을 뜻하지 않는다. 반복 클릭마다 문구 내부 DOM을 새로 갱신한다.

| ID | 처리 완료 selector | 정확한 문구 | 별도로 검사할 결과 |
|---|---|---|---|
| B01 | `coupon-status` | 쿠폰 확인 완료 | 할인 금액·적용 쿠폰·최종 금액 |
| B02 | `quantity-status` | 수량 확인 완료 | 해당 행의 수량·행 금액·상품 합계 |
| B03 | `restock-status` | 재입고 알림 안내 확인 완료 | `restock-dialog` 표시 여부 |
| B04 | `category-status` | 카테고리 선택 확인 완료 | 현재 URL·검색 결과 |
| B05 | `favorite-status` | 찜 상태 확인 완료 | 버튼 문구·하트 상태·찜 개수 |
| B06 | `delivery-status` | 닫기 요청 확인 완료 | `delivery-dialog` 표시 여부·배경 잠금 |

모든 selector는 `data-testid` 값이다. B06 확인 문구는 팝업 밖 body에 있으므로 실제 닫기 수정 후에도 유지할 수 있다.
수정 시 확인 문구를 제거하거나 성공 결과로 대체하지 말고, 같은 문구를 해당 작업 완료 뒤 갱신한다. 비동기 작업은 실제 응답을 기다린다.
새 결함이 재현되려면 연타가 필요한 것은 아니다. 한 번의 기능 클릭으로 재현하고, 사용자 연타는 SDK 신고 안내를 여는 용도로 구분한다.
현재 로컬 SDK `rage.ts`는 주 포인터의 왼쪽 입력을 같은 위치 반경 30px 안에서 1초 내 3회 감지하며 60초의 재안내 대기 시간을 둔다.
이는 소스 확인이며 실제 배포 SDK·플랫폼 통합 검증 결과는 아니다. Enter는 포인터 연타 감지 대상이 아니다.

`src/composables/useActionNotice.js`와 `src/components/ActionNotice.vue`는 확인 문구의 반복 갱신을 공통 처리한다.
재입고 신청창은 안내 UI만 제공하며 실제 알림 등록·발송 API는 이번 범위에 없다. B03의 판정 범위는 창이 열리는지까지다.
결함 위치에 `INJECTED DEFECT B0x` 주석을 두고, 화면·API 응답에 정답이나 결함 ID를 노출하지 않는다.

## 4. 제거한 v2 결함

- **B01 키보드 쿠폰 중복 적용**: 서버의 상품 예외를 제거했다. 어떤 상품이든 동일 코드 재적용은 409로 거부한다. 화면도 서버 이력 기준으로 중복을 판단한다.
- **B02 마우스 감소 후 합계 잔류**: 모든 수량 변경에서 서버 합계를 다시 계산한다. 새 결함은 화면의 증가 버튼에만 있다.
- **B03 추천 진입 후 품절 버튼 활성화**: 구매 버튼은 현재 상품의 `soldOut`에서 계산한다. 어떤 추천 경로로 들어가도 한정판 담기는 비활성화된다.
- **B04 허브 빠른 담기 중복 요청**: 카드의 상위 위임 리스너를 제거했다. 검색 빠른 담기 1회는 요청 1회·상품 1개다.
- **B05 매트 찜 UUID 손상·삭제 404 무시**: 서버 UUID를 그대로 유지하며 실패 시 롤백·오류 표시한다. 찜 목록에서 조회 후 해제도 정상이다.
- **B06 받침대 팝업의 라우트 이탈 잔류**: 모든 상품의 라우트 이탈 때 팝업을 닫고 배경 잠금을 해제한다.

기존 DB의 잘못된 중복 쿠폰 이력·subtotal은 자동으로 변경하지 않는다. 발표용 상태는 승인된 초기화 절차를 사용한다.
정상 품절 정책 N01·비활성 주문 버튼·검색 결과 없음·인증 요구·수량 상한은 새 결함으로 취급하지 않는다.

## 5. 검증

`tests/demo_browser.py`는 임시 dev/production DB·동적 포트·Chromium을 사용한다.
B01/B02는 재고 있는 5종, B03은 직접·새로고침·홈·검색·다른 상품 5종의 추천 경로,
B04는 홈·다른 검색·상품 6종과 두 헤더 메뉴, B05/B06은 상품 6종을 검사한다.
반복 클릭의 확인 문구 DOM 갱신, 서버 상태 불변, 정상 대조와 제거한 v2 결함도 확인한다.
B03/B04/B06은 비로그인으로 실행한다. 계정이 필요한 사례는 dev reset 후 정상 로그인, production 격리 계정 가입으로 준비한다.
실행 결과와 검증하지 않은 범위는 [검증 기록](./DEMO_VERIFICATION.md)을 참고한다.
일반 브라우저 검증 통과는 SPEAR 엔진 실행·SDK 신고·수정 배포 후 재검증 통과를 뜻하지 않는다.
